What I Learned:
This lesson showed how systemd can be used to deploy and manage an application as a Linux service.
The instructor used a Node.js application as the example, but the same concepts can be applied to our Java Robot World application. Instead of manually starting the Robot World server every time, it could be configured as a systemd service and managed using systemctl.

Why Use systemd for an Application?
An application server can be registered as a systemd service instead of being started manually.
For our Robot World project, this would mean that the Java server could be managed like any other Linux service.
systemd can provide:
•	Automatic startup when the system boots.
•	Automatic recovery if the application crashes.
•	Centralized management using systemctl.
•	Integration with systemd logging.
•	No need to manually start the Java server after every reboot.

The main idea is:
systemd turns an application from a manually managed process into a properly managed Linux service.

Installing the Application Environment
The instructor's example uses Node.js, but for my Robot World project the application environment would be Java.

The same general deployment process applies:
Install the required environment → Obtain the application → Configure the application → Create a systemd service
For Robot World, this would involve having the required Java runtime available and deploying the built Java application, such as the packaged JAR produced by Maven.
The important concept is that the server application needs its required runtime and application files available before systemd can start it.

Custom systemd Services
RHEL allows administrators to create custom systemd services for applications that are not built-in system services.

Custom unit files are placed under:
/etc/systemd/system/

A service unit file describes how systemd should run and manage the application.
Important settings include:
•	Description → describes the application service.
•	Network dependency → specifies that the application should start after networking is available.
•	WorkingDirectory → specifies where the application is located.
•	ExecStart → specifies the command used to start the application.
•	Restart → determines what happens if the application fails.
•	User → specifies which Linux user runs the application.

For Robot World, ExecStart would represent the command used to start the Java server, rather than a Node.js application.

Why the User Matters
An application does not need to run as root.
Running the Robot World server under a dedicated or normal Linux user follows the principle of least privilege. This limits what the application can access if the application is compromised.
This is an important deployment and security consideration.

Making systemd Recognise a New Service
After creating or modifying a .service file under /etc/systemd/system/, systemd needs to reload its configuration:
sudo systemctl daemon-reload
This tells systemd to re-read its unit files and recognise the new or modified service.
Enable and Start the Application

Once the Robot World service has been configured, it can be enabled and started:
sudo systemctl enable --now robotworld
This performs two actions:
•	enable → configures the service to start automatically at boot.
•	--now → starts the service immediately.

The service can then be checked with:
systemctl status robotworld
This allows an administrator to verify whether the Robot World server is currently running and whether it is enabled to start automatically.

Application Ports and firewalld
The Robot World server needs to listen on a network port so that clients can connect to it.
This connects directly to what I learned about firewalld.
Even when the Java server is running correctly, the firewall can prevent clients from reaching it.
The required application port therefore needs to be allowed through firewalld.

For example, if the Robot World server is configured to listen on port 5050:
sudo firewall-cmd --add-port=5050/tcp
This allows the port in the runtime firewall configuration.
To make the rule persistent:
sudo firewall-cmd --add-port=5050/tcp --permanent

The important concept is:
Application running ≠ application reachable
For a client to connect successfully:
Java server → listening on port → firewall allows traffic → Robot World client connects

Deploy the Robot World application
↓

↓

Overall Understanding
The main thing I took from this lesson is that deploying an application on Linux is not just about getting the application to run. It also involves making the application manageable, reliable, secure, and reachable.
For my Robot World project, systemd could take the Java server that I previously started manually and manage it as a proper Linux service. This would allow the server to start automatically, recover from failures, and be controlled through standard system administration commands.
